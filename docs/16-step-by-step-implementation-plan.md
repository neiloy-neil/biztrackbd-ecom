## 1. Principles

1. **Walking skeleton first.** One real COD order for one tenant, end to end, before anything is widened.
2. **Five visual templates, shared commerce core:** `kapor`, `gadgetstudio`, `mini-bunny`, `axionwear`, and `bindu` ship on one tenant-aware renderer. Industry behavior remains in optional modules (doc 06).
3. **First sellable product is Phase 5.** A merchant can sign up, pay by manual bKash or Nagad, and be approved by you. Everything before it makes the store work; everything after it makes it better.
4. **Port, do not rewrite.** The five existing projects already contain Prisma models, order logic and admin screens. Lift working code into the packages below.
5. **Canvas is the UI reference** (doc 09). Components come from `packages/ui`.
6. **Limits and prices live in the `Plan` table**, not in code.
7. **Scope fences:** single warehouse, no physical POS, no marketplace, no chatbot ordering before the pilot.

### Phase 1: Core Engine (weeks 3 to 4)
- **Tasks:** AES-256-GCM secrets vault and `TenantIntegration` (doc 04, 17); `Plan` and `UsageCounter` with limit enforcement (hard on products, soft 10% on orders); staff roles and invites; audit log; Supabase Auth for the three actor types; edge hostname routing with Edge Config (doc 13).
- **Phase 1 status:** the secrets vault and `TenantIntegration` are built and tested (21 tests, doc 17 section 2), with an admin Integrations screen (write-only key fields). Plan limits are built too (below). Staff roles, invites and the audit log are built too (below). Edge hostname routing is built too (below). Still to do: Supabase Auth, real Inngest.
- **Plan limits (built):** `packages/core/src/limits/plan.ts`, `products/service.ts`, 18 tests in `tests/limits.test.ts`.
  - Products are a hard cap. The slot is claimed in one atomic `UPDATE "Tenant" SET "productCount" = "productCount" + 1 WHERE ... <= limit`, inside the same transaction as the insert, so racing creates cannot overshoot and a failed insert returns the slot. Delete frees it once; restore claims one again. `Tenant.productCount` is the counter; `reconcileProductCount()` repairs drift.
  - Orders are soft. Every new order (not a replay, not a failed one) increments the monthly `UsageCounter` row for the store's own timezone month. Checkout is never blocked. The counter moves one step at a time, so "value equals 80%, 100% or 110% of the limit" fires `usage/threshold-crossed` exactly once even under concurrency. Past 110% the state is `exceeded`: orders still go through and the admin shows the upgrade prompt.
  - Limits are read live from `Plan.limits` (null = unlimited), so a plan edit applies at once. A downgrade keeps existing products and blocks new ones.
  - `Tenant.orderCountMonth` in doc 08 is no longer used; `UsageCounter` is the source for orders.
  - Admin: Products (add and delete, upgrade prompt at the cap) and Plan and usage (meters and warnings).
- **Staff roles, invites and audit log (built):** `packages/core/src/permissions.ts`, `staff/service.ts`, `audit/service.ts`; 23 tests in `tests/staff.test.ts`; admin Team, Audit log and invite-accept pages.
  - Roles use the five `StaffRole` values. Canvas columns map to them: Manager = `STORE_MANAGER`, Staff = `ORDER_PACKER`, Support = `TELEMARKETER`. `CONTENT_EDITOR` is not on the canvas yet (catalog and design only). One owner per store; the owner's role cannot be changed or given away (ownership transfer is a later feature).
  - Permission areas: orders, products, customers, marketing, reports, design, billing (payments, domains, billing and integration keys), team (staff and audit log). Levels none, view, edit. The matrix is one constant; the admin checks it on every page (redirect to "no access") and again inside every server action. Services that take an `actor` check it too.
  - Invites: 32-byte random token, only its SHA-256 stored, 7-day expiry, one-time (a single conditional UPDATE claims it). Unknown, used, revoked and expired links all give the same message. The staff plan limit counts active accounts plus open invites, and a per-store row lock stops two invites taking the last seat. Until Brevo exists (Phase 4) the owner copies the link.
  - Audit log: written in the same transaction as the change (no change without a line, no line for a rolled-back change). Append-only for the app role at the database level (migration 4 revokes UPDATE, DELETE, TRUNCATE). Details are redacted by key name (secret, password, token, api key, cipher, authorization), and integration entries record only which fields changed. Recorded so far: staff, integration, product and Mark as paid actions.
  - Accepted staff get a placeholder credential (`EXTERNAL_AUTH`) until Supabase Auth. The admin session is a dev stub that loads a real `TenantUser` chosen by cookie, so each role can be tried; it refuses to run in production. *(Historical snapshot: real sign-in, the platform team's two-step sign-in and Supabase picture storage were built in Phase 10, see below.)*
- **Edge hostname routing (built):** `apps/storefront/src/proxy.ts`, `packages/core/src/routing/*`, `domains/service.ts`, migration 5; 55 tests (`routing.test.ts`, `domains.test.ts`). Design and rules in doc 13 section 2.
  - Verified in the browser and with curl against the running storefront: store subdomain, platform root and www, unknown, reserved, nested look-alike, IP and unverified hosts (404), case and port normalisation, spoofed `x-bt-*` headers ignored, a verified custom domain with www and subdomain 308 redirects to the primary (path and query kept), and a suspended store (503 offline page) serving again after reactivation.
  - Domains: adding needs the plan feature `customDomain` (Starter has it off) and the owner role, max 5 per store, audit-logged. An unverified claim routes nothing and blocks others for 24 hours, after which a new claimant can take the name; a verified claim never expires. Errors never reveal which store holds a domain. At most one primary per store (partial unique index); removing the primary promotes the oldest verified one.
  - `confirmDomainVerified` is for the platform's DNS check and is deliberately not exposed in the store admin. Phase 7 added that check (`domains/verify.ts`), so a domain now verifies itself once its DNS record is right.
  - Edge Config sync is implemented and tested against a fake `fetch` only. Proxy cache means a change made in the admin reaches the storefront within 15 seconds on self-hosting, immediately with Edge Config.
  - `Tenant.customDomain` in doc 08 is not used; the `Domain` table is the source.
- **Acceptance:** limits block product creation at the cap and warn at 100% of orders; secrets never leave the server; roles restrict screens.

### Phase 4: Couriers, Fraud, Returns, COD Settlement, Profit (weeks 9 to 13)
- **Tasks:** courier adapters Steadfast first, then Pathao and RedX (doc 10); `AdmIntegrations` key entry; `MobCourier` booking sheet; courier webhooks and 30-minute status sync; hybrid fraud check (`PhoneTrustStat` plus per-store `BlockedContact`, doc 12) with `AdmFraud` and `MobFraud`; returns and exchanges (`AdmReturns`); COD reconciliation (`AdmCodRecon`, `MobCodRecon`, doc 28); profit and loss with `Expense` (`AdmProfit`).
- **Phase 4 status (built, with the gaps below):** migration 9, `packages/core/src/{couriers,fraud,returns,finance}`, and admin screens Returns, Fraud check, COD payouts and Profit and loss, plus a courier card and a delivery-trust card on every order.
  - **Couriers** (`couriers/`): adapters for Steadfast, Pathao and RedX behind one interface (`book`, `status`, `verify`, `parseWebhook`), each mapping the courier's own status words onto `BOOKED, PICKED_UP, IN_TRANSIT, HOLD, DELIVERED, RETURNED, REFUSED`. Booking (`bookCourier`, `bookCouriers`) is a paid-plan feature (`Plan.features.courierBooking = "auto"`; Starter hand-ships). The courier call is made outside any transaction, so the order is first claimed with a 2-minute lock (`Order.courierBookingLock`): two clicks or two staff reach the courier once; a courier refusal releases the lock; a lost reply (timeout) keeps it, so a second parcel is never booked blind. A confirmed order is packed on the way out, so the state log reads PENDING, CONFIRMED, PROCESSING, SHIPPED. COD collects `totalAmount`; an order already paid collects 0. Orders held for fraud review, unconfirmed orders and unpaid mobile-money orders are refused.
  - **Status follow-up:** webhooks at `/api/webhooks/courier/<integration token>` (no sign-in; the 192-bit token in the address names the store, the adapter checks the message, Pathao's `X-PATHAO-SIGNATURE` HMAC is checked when sent), a de-duplication key per message in `CourierEvent` (append-only), progress that arrives late or out of order is ignored, delivered can never be overwritten by in-transit, unknown parcels are answered 200 and logged, and the raw message is kept with secret-looking keys redacted. The 30-minute sync (`syncCourierStatuses`, `syncAllStores`, `/api/cron/courier-sync` behind `CRON_SECRET`) catches whatever the webhooks missed; the order screen has "Check status now" and the COD screen "Sync couriers now". RedX has no callback, so it relies on the sync. The Integrations screen has a "Test connection" button (records the result on the integration) and shows the store's status address to paste into the courier's portal.
  - **Delivery bookkeeping in `transitionOrder`:** delivered sets `deliveredAt`, marks a cash-on-delivery order paid (whoever delivered it collected the cash), and sets `settlementStatus` to `COLLECTED_UNSETTLED` only for a courier parcel with cash still to come (otherwise `SETTLED`). Returned sets `returnedAt` and `refusedAtDoor` (the order screen asks "did the customer refuse it?"), restocks as before.
  - **Fraud** (`fraud/`, doc 12): per-number delivery trust from a platform-wide record of outcomes (`PhoneTrustEvent`: salted phone hash, order hash, store hash, outcome, time; `PhoneTrustStat` is kept as the aggregate). The app role cannot read either table; it reaches them through two `SECURITY DEFINER` functions (`phone_trust_record`, `phone_trust_lookup`) that take only hashes and return only counts by age. Score is the recency-weighted delivery ratio (1.0 / 0.8 / 0.5) times 100 minus 10 per door refusal in 60 days; above 75 trusted, 50 to 75 medium, below 50 high, and a single bad parcel is capped at medium. Every new order is scored inside its own transaction (replacing the Phase 0 placeholder): first-time buyer, low delivery success, cash on delivery over ৳5,000 from a number with no delivered parcel, incomplete address, and one number used for different districts within 30 days (10 points each). A cash-on-delivery order from a high-risk number placed by the customer is held (`Order.fraudReview = HELD`) and cannot be booked until the owner releases it; prepaid orders and orders staff key in after a call are scored but never held. Owner controls: release or re-hold with a note, per-store blocklist (`BlockedContact`), number lookup, and an overview (held, risky in 30 days, blocked, cash orders stopped). Every one is audit-logged.
  - **Returns** (`returns/`): `PENDING, APPROVED, PICKUP_BOOKED, RECEIVED, REFUNDED` or `EXCHANGED`, or `DECLINED`. Only a delivered order can have a return; a unit cannot be in two live returns; `RT-0001` codes are per store and race-safe. An exchange sets the replacement aside at approval (stock moves are in `StockAdjustment`) and gives it back if the return is declined; good goods are restocked on receipt (damaged ones are not). A refund is bKash or Nagad send-money (with the owner's own TrxID) or store credit (`Customer.storeCredit`); the order is locked so concurrent refunds cannot pay out more than the customer paid; a full refund closes the order as `REFUNDED`. `RefundLedger` is the record.
  - **COD reconciliation** (`finance/cod.ts`): expected payout per parcel = cash collected minus the courier's delivery charge minus the COD fee, from the real figure when the courier told us, else from the owner's rates (`StoreSettings.courierFeeInsideDhaka`, `courierFeeOutsideDhaka`, `courierCodFeePercent`, edited in Delivery charges). A payout CSV is read by header name (many spellings per column, a title line above the header, quoted cells, ৳ and Bangla digits), each row is matched to a parcel by consignment ID, tracking code or order number for that courier only, and the line is `MATCHED`, `SHORT_PAID` (more than ৳1 below expected, with a plain-words guess: fee taken twice, outside-Dhaka rate, cash not paid out) or `RETURNED`. The same payout invoice or the same parcel cannot be counted twice. The screen shows what couriers owe (by courier), what is overdue (over 7 days), what was received and what the couriers charged this month, and what does not match; "Mark matched" accepts a short payment and "Raise dispute" leaves a note on the order.
  - **Profit** (`finance/profit.ts`): delivered sales minus product cost, courier delivery fees, courier COD fees, return losses, refunds paid in cash, gateway fees (none yet) and owner-entered costs (`Expense`: ads, packaging, rent and salaries, other). Everything is summed in whole paisa per day, so the lines, the days and the headline always agree exactly. Product cost is snapshotted on each order item (`OrderItem.unitCost`), with a warning when items have none.
  - **Permissions:** booking, returns and fraud actions need `orders` edit (so a fulfilment packer can book); blocking needs `customers` edit; the COD and profit screens are visible to the owner and manager (`reports` view) and changed only by the owner (`reports` edit).
  - **Acceptance, measured:** `pnpm --filter @biztrackbd/core test` 17 files, 366 tests (97 new: adapters against a fake `fetch`, booking races, webhook de-duplication and ordering, trust, holds, returns, statements, profit); `pnpm --filter @biztrackbd/db test` 27 (a new platform table the app role cannot touch); Playwright `pnpm --filter @biztrackbd/admin e2e` runs a customer order, a booking against the local fake Steadfast (`e2e/fake-courier.mjs`), a delivered callback sent twice, a status check, a statement import with one short payment, the profit totals equal to the sum of their lines, a return to a refund, and a risky number held then released, at 390 and 1440, and every new screen passes axe, has no sideways scroll and (on phone) 40px tap targets.
  - **Not done, and not verified:** the three courier adapters were written from the courier docs and tested against fakes only; they have not been run against real Steadfast, Pathao or RedX accounts, so the first live booking per courier should be done on a test parcel and its status words compared with the maps in `couriers/*.ts` (an unknown word changes nothing and is logged). Pathao books by address text (no city and zone ids) and its webhook registration handshake is not answered; RedX needs `pickupStoreId` set to book from a specific store. The Pathao token cache is per process (docs/10 says shared storage, Phase 7). Return pickups are recorded by hand, not booked with the courier. Store credit can be issued but not yet spent at checkout. Customers cannot open a return themselves (the storefront returns page is still not built). The 30-minute sync needs a scheduler pointed at `/api/cron/courier-sync` (Inngest is still a seam). SMS and email confirmations (OTP before booking, "your parcel is booked") wait for Phase 5/6 messaging. A phone number's outcomes are never forgotten; deletion on request is not built. The exchange does not settle a price difference. `PhoneTrustStat.storesSeen` is computed from the event table. The expected-fee estimate treats the district Dhaka as inside Dhaka.
- **Acceptance:** booking a parcel calls Steadfast; a statement import marks short-paid parcels; P&L totals equal the sum of its lines.

### Phase 9: Loyalty, VIP levels, referrals, pages and blog (after Phase 8; the owner chose "post-pilot features")
- **Tasks done:** loyalty points, a four-level VIP system and double-sided referrals (docs/26); pages and a blog (`AdmPagesBlog`); the admin screens `/marketing/loyalty` and `/content`; the customer's rewards on the account page, the points pill in the header, points and the friend's offer at checkout, the referral link `/ref/<code>`.
- **Status (built and measured; the pilot has not happened, so none of it has met a real customer):** migration 13 and `packages/core/src/{loyalty,content}/`.
  - **Earning** (`loyalty/engine.ts`): when a program is on, an order writes a PENDING earn for the amount actually paid for the goods (after coupon, VIP, friend and points discounts, not delivery), at the multiplier of the level the customer holds when ordering. It unlocks when the order is delivered, once (a conditional update on the row and a unique index on account, order and kind); a cancelled order voids it; a returned or refunded delivered order takes it back (never below zero) and re-rates the level. Staff-keyed and landing-page orders earn too.
  - **Spending:** whole blocks (default 10 points = ৳10), no more than the balance and no more than the store's share of the cart (default 30%). The points are taken in the order's own transaction with a compare-and-take update, so two orders cannot spend the same points (four racing orders for one balance: exactly one placed). A cancelled order gives them back. **Spending points and the VIP discount need a signed-in customer:** the storefront passes the customer id from the signed session cookie, never from the browser, and only when it is the customer of the number being ordered with. A phone number typed into a form is not proof, so a guest gets nothing even if they type a Gold customer's number.
  - **VIP levels:** Silver (৳5,000 delivered in the last 12 months, 1.25x points), Gold (৳15,000, 1.5x, 5% off every order), Platinum (৳35,000, 2x, 10% off, free delivery everywhere). The 12-month spend is recomputed from the delivered orders each time, never incremented, so it cannot drift. The thresholds are fixed in code, not settings. A customer who moves up is sent one SMS.

A cancelled friend's order frees the offer again.

Published pages appear in the footer, posts in `/blog` and both in the sitemap; drafts are invisible to customers.
